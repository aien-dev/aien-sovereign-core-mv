## Findings

- **Conditional cleanup hang (Important for configurations that fail ownership detection):** `ChromeProcess::reap` has a nominal five-second deadline, but after that deadline it unconditionally calls blocking `self.child.wait()` (lines 665–670). If the direct child is still alive and was not matched/signaled—e.g. a renamed/non-Chrome executable whose environment tag was scrubbed and whose rewritten title is deliberately rejected by the Chrome-image gate—`Drop` can block indefinitely. The current checks fail closed (no unsafe numeric signal), but the deadline is not a bound on drop latency. This is conditional on an executable/process state outside the qualified Chrome-image fallback; do not treat it as a demonstrated failure for the tested Chrome 153 path. Reproduction proposal: use a controlled long-lived `AIEN_CHROME` fixture that accepts the startup arguments, removes the tag and rewrites its title, with a non-allowlisted `/proc/<pid>/exe` basename; cause teardown while it remains alive and observe that cleanup reaches the final `wait()` and does not return. Do not run this without an explicit safe fixture and process-cleanup plan.

- **Profile-argument fallback is a discriminator, not an authenticated launch relationship:** `has_browser_identity` accepts an exact `--user-data-dir=<private path>` argv field for any executable before consulting the Chrome-only rewritten-title fallback (lines 510–525). This is consistent with the documented fallback and raw-argv fixture, and avoids arbitrary substring/prefix matches. It does mean an unrelated process deliberately or accidentally carrying that exact argument is treated as owned and can be pidfd-killed. The 0700 profile directory protects its contents, not the argument's provenance. This is only a concern if the contract is intended to defend against same-UID processes that can learn/reuse the profile path; same-UID adversarial signaling is not otherwise a privilege boundary. A targeted negative-control reproduction would launch a harmless long-lived foreign fixture with the exact profile argument but no tag, then check whether cleanup classifies it. Existing fixture coverage proves the positive match and neighboring-prefix rejection, not this exact-argument foreign case.

## Correctness checked statically

- Linux startup refuses when pidfd open/send-signal capability is unavailable (`spawn`, lines 404–408); `available()` probes both operations on the current process (583–585).
- Discovery PIDs remain hints. `open_owned` obtains a pidfd first, then rechecks exact tag or profile identity, and sends SIGKILL only through that descriptor (592–617). PID reuse after pinning cannot redirect the signal to a replacement task.
- Rewritten single-title matching requires one cmdline string, an allowlisted executable basename, exact `/proc/<pid>/exe` prefix, and the complete profile flag with a right delimiter (527–550). A non-Chrome image is not accepted via title fallback; that boundary is the conditional cleanup case above.
- Spawn failure removes the newly created profile directory (439–444). Errors after the child has been stored return through its `Drop` cleanup; early exit records `main_reaped` before returning (446–475). Drop attempts cleanup before removing the profile (674–678).
- `ECHILD` is treated as already reaped (657–660), and Linux teardown contains no numeric PID/group signal. The profile scan and pidfd revalidation are repeated until no candidates remain or the deadline is reached. The final blocking `wait()` means timeout is not a hard upper bound in the missed-child case.
