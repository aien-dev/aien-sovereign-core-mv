Two first attempts of the HTTP gate, kept as they happened:
- try1-http-w4-12gib-chip-error-no-lock: the server could not open a chip channel (RM_ALLOC status 0x51) while it ran without the shared chip lock.
- try1-http-fp8-12gib-gate-asked-wrong-model-name: the server loaded and stayed inside 12 GiB (health.json), but the gate script asked for model "x" and every request was refused; the three MATCH lines compare empty replies and the control also said MATCH, so the verdict was FAIL.
Fix (tools/rig/http-gate.sh): the server now runs under the chip lock, the model id is read from /v1/models, and an empty reply can never pass.
- try2-http-w4-12gib-flock-deadlock: my fix wrapped the server in flock; the server takes the same chip lock itself, so it waited on its own lock for 21 minutes (0 percent CPU, in flock(2)) and I stopped it. Fixed: tools/rig/http-gate.sh no longer wraps the server.
- try3-http-w4-12gib-chip-no-memory: no flock this time, queued behind other jobs for the lock, then the chip channel failed with NV_ERR_NO_MEMORY (kernel log: kgrctxAllocMainCtxBuffer) because the box was short of free memory at that moment (MemFree 9.5 GiB, MemAvailable 11.9 GiB; other agents run 27B servers). Fix: tools/rig/http-gate.sh waits for MemFree >= 16 GiB before each start and retries the start up to 6 times, keeping every failed attempt log.
- try4-http-fp8-12gib-ids-shifted-by-refused-request: loaded (two earlier NO_MEMORY starts retried, see ground.txt), stayed inside 12 GiB, served 22 tok/s, and the first two gate replies match the host reference with the control failing as it must; but the second request was refused by the server (GPU busy: another job held the chip lock for 300 s), left no line in the ids log, so the third comparison paired the wrong prompt. Fix: tools/rig/http-gate.sh retries refused requests until they are answered. Rerun below.
- try5-http-w4-12gib-first-request-refused: the first start worked (MXFP4, 9.1 GiB on the card, 28 to 29 tok/s through HTTP), but the very first gate request was refused as GPU busy before the retry fix, so the ids shifted by one: the two comparisons that were made (Rust prompt and the plain-words prompt, 64 tokens each) MATCH the MXFP4 host reference and their controls fail, the third paired a 256-token speed request with a 64-token reference and cannot match. Rerun below with the retry fix.
