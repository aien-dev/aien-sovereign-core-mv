# Persistent KV benchmark (cut C9, sc#485)

Binding design: ADR 0003 (sections 10, 15.1, 16.5). Cut and schema: CUTS.md C9 (B6, B7, B8). Evidence rules: ADR 0001 decisions 2 and 3.

## What this measures

`bench_persistent_kv` runs conversations through the real runtime: the spine, the scheduler, `NativeTransformerBackend` over `ReferenceCpuBackend` (host CPU arithmetic, bf16 KV pool) with the synthetic reference test weights, and, for the restore mode, the C4 host filesystem store switched on through the daemon wiring (`shared_kv::enable_persistent_kv`). Host only: no GPU, no CUDA, no root.

Each row is one mode at one concurrency (1, 2, 4, 8 conversations) and one prompt length (512, 2048 tokens), repeated for a number of rounds:

| mode | workload | what happens | cache_state |
|---|---|---|---|
| `resident-only` | `single_turn` | one request per conversation, store off; nothing ever leaves memory | `none` |
| `cold-prefill` | `second_turn` | turn 1, then turn 2 (turn-1 prompt + turn-1 output + 16 new tokens), store off; turn 2 prefills everything | `none` |
| `restore-from-page-cache` | `second_turn` | the same turns with the store on: turn 1 parks, turn 2 restores the stored prefix and prefills only the rest. The objects were written moments before and no cache was dropped. A row is refused unless every measured request committed a restore | `page_cache` |
| `restore-from-device` | | NOT_RUN: a device read needs the page cache dropped (root) and verified empty (ADR 15.1); the harness never uses sudo | `device` |
| `native-physical` (Spark, Pi 5) | | NOT_RUN in every report (B8): a host run cannot speak for native hardware | `device` |

Only the turn-2 requests (or the single turn of `resident-only`) are timed. Every report records, per row: completed and failed requests, request latency p50/p95, time to first token p50/p95, decode tokens per second, the KV pool allocation, the peak holder bytes, the staging bytes, the peak RSS, the store dispatch depth, the restored token count, and every raw sample. The exact definition of each field is written into the report itself (`definitions`).

Rules the binary enforces (tests in `crates/aien-kv-bench/tests/bench_persistent_kv_test.rs`):

- no row without its mode, platform and cache_state labels, and no default mode (B7);
- no measured row without every metric of the B6 schema, percentiles that match the raw samples, and at least one completed request (B6);
- latency summaries never mix cache states (ADR 15.1);
- every report carries the Spark-native and Pi 5 physical rows as NOT_RUN with a reason, and refuses measured numbers for any platform other than `hosted` (B8);
- a report is never overwritten; it records the commit, whether the tree was clean, the machine, the nice value, the exact command and the sha256 of the raw samples.

## How to reproduce

```
cargo build --release -p aien-kv-bench --bin bench_persistent_kv
nice -n 19 ./target/release/bench_persistent_kv \
  --modes resident-only,cold-prefill,restore-from-page-cache,restore-from-device \
  --concurrency 1,2,4,8 --prompt-tokens 512,2048 --rounds 10 \
  --out benchmarks/data/persistent_kv_host_<UTC stamp>.json --store-root target/pkv-bench-store
./target/release/bench_persistent_kv --render benchmarks/data/persistent_kv_host_<UTC stamp>.json
```

`--render` re-checks the report (schema, labels, NOT_RUN rows, samples digest) and prints the table below.

## Where the numbers live (ADR 0001)

The canonical record is the JSON file in `benchmarks/data/`, named by its measurement id. ADR 0001 names `benchmarks/data/benchmarks_latest.json` and a `sync-docs` tool; neither exists in the repository (also recorded in `docs/plans/public-surface-cleanup.md`). DOCS SILENT choice, narrowest rule: this bench writes its own file and never edits `latest.json`, `master_benchmark_results.json` or the inference sweep files, and the table below is generated by `--render` from that file, not typed by hand.

## What the run shows, and what it does not

- The numbers come from a tiny synthetic model on the CPU. They show how the harness and the persistent KV path behave against each other on this machine; they say nothing about real model speed, GB10 speed, or NVMe speed.
- Turn-2 requests that restore their prefix from the page cache reach their first token sooner than the same requests prefilled cold, at every concurrency of this run (compare `ttft` of `cold-prefill` and `restore-from-page-cache` in the table).
- Store bounds (finding of the first full run, refused by the row guard and not recorded): with the default per-class bounds (48 restore, 16 park at the time, ADR 7.1), 8 conversations finishing in the same step submit 24 chunk parks and 8 are refused `QueueFull`. That is the designed behaviour (not parked this turn, the next turn prefills), but it means the defaults are too small for 8 simultaneous finishes. The bench now sets `AIEN_KV_STORE_MAX_RESTORE_OPS` and `AIEN_KV_STORE_MAX_PARK_OPS` to concurrency times the chunks per turn plus one; the park default is now 64 (ADR 0003 section 18.4).
- `resident-only` is a single turn, so its latency is not a turn-2 number; it is the reference for a conversation that never leaves memory (this runtime has no cross-request resident prefix reuse to measure a resident turn 2).
- Not measured: device reads, O_DIRECT, the queue-depth sweep, CPU time per MiB and the device ceiling (cut X1), and every native row.
